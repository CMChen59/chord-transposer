## 📅 2026-11-18：專案啟動、需求分析與架構確立

### 1. 初始需求討論
- **核心目標**：
  1. **和弦轉調功能**：依據所需調性，提供對應的新調性和弦。
  2. **和弦組成音查詢**：能夠清楚知道每個和弦的組成音。
  3. **PDF / JPG 和弦譜判讀**：最終能直接讀取 PDF 或 JPG 格式的和弦譜並轉換為目標調性。
- **可行性與技術架構結論**：
  - **核心樂理運算（低難度）**：12 平均律半音位移與和弦結構公式固定，需特別處理五度圈同音異名（Enharmonic，如 `Bb` 與 `A#` 的選擇）。
  - **視覺辨識（中高難度）**：傳統 OCR 容易誤判上下標、`#`/`b` 與外框，決定採用 **Web 前端 (`PDF.js` + Canvas) 搭配 Gemini Vision API** 的架構。

---

### 2. Gemini Vision API Token 消耗與成本評估
- **討論重點**：串接 Gemini Vision API 是否會消耗大量 Token？
- **決策結論**：
  - **辨識 1 次，無限次免費轉調**：只有「首次上傳圖片辨識出和弦結構」時會呼叫 1 次 API；後續所有的轉調計算、切換顯示模式、查詢組成音，100% 由瀏覽器端 JavaScript 樂理引擎即時運算（消耗 0 Token）。
  - **免費額度充足**：Google AI Studio 提供的 Gemini Flash 免費方案每日有數百至上千次額度，個人練琴抓譜完全免費。

### 3. 實際樂譜樣本深度分析
使用者提供兩份實際使用的電子琴／編曲機專用簡譜進行評估：

1. **樣本一：《償還》(2 頁式掃描型 PDF)**
   - **特徵**：預設調性 `Am`（建議女調 `Cm`、男調 `Fm`）。譜面上的和弦包在**圓角方框**內，採用**簡譜級數和弦**標記法（如 `6m`, `2m`, `37`, `67`, `37-9+5`, `4M7`, `5m6/7b`, `/5`）。
   - **技術對策**：需建立「簡譜級數和弦解析器」，讀懂 `-9` (`b9`)、`+5` (`#5`) 與分數轉位語法，並能根據目標調性換算為對應和弦。

2. **樣本二：《川の流れのように》(單頁 JPG 圖片譜)**
   - **特徵**：預設調性 `C`（建議 `C+2`，`1=D`）。譜面上的和弦為**紅色英文字母和弦**（如 `C`, `Am`, `Dm`, `Gsus4`, `CM7`, `bE`）。
   - **技術對策**：需相容華文簡譜常見的「前置升降記號」（如 `bE` 即 `Eb`），並在視覺辨識時自動過濾藍色的 `R1~R8`（註冊記憶）、紫色的 `Style-1 Main A`、綠色的 `Fill B` 等電子琴控制標記。

### 4. 和弦表示法決策（英文字母 vs. 數字和弦）
- **討論脈絡**：
  - 使用者思考：若未來希望練就不靠工具、純靠自己大腦轉調，數字表示法（如 Am 轉 Cm 時：`6m => 1m`、`2m => 4m`、`37 => 57`）是否更有規律？但日常使用上其實更偏好直接看「英文字母和弦（`Cm`, `Fm`, `G7`）」。
- **最終設計決策（兼顧日常直覺與練功需求）**：
  - 底層建立統一的樂理資料模型，介面提供**一鍵切換顯示模式**：
    1. **【英文字母模式（預設）】**：統一顯示為 `Cm`、`Fm`、`G7`、`AbM7`，最符合日常看譜與電子琴螢幕顯示習慣。
    2. **【固定調數字模式】**：顯示為 `1m`、`4m`、`57`、`b6M7`（並自動幫使用者標出黑鍵升降號，避免 `3-4`、`7-1` 半音換算錯誤）。
    3. **【練功對照模式】**：並列顯示 `6m ➔ Cm (1m)`，在看英文和弦彈琴的同時自然記憶級數對應規律。
  - **組成音顯示**：點擊任何和弦時，同時顯示**英文音名 (`C - Eb - G`)**、**簡譜數字 (`1 - b3 - 5`)** 以及**互動式鋼琴鍵盤圖示**。

### 11. 執行任務 T2-1：建立樂譜檔案載入與高清畫布預覽模組 (`js/sheet-viewer.js`)
- **實作重點**：
  1. **新增「📄 模式二：琴譜 PDF / JPG 載入與轉調」分頁**：支援拖曳上傳 (Drag & Drop) 或檔案選擇器載入任何 `.pdf`, `.jpg`, `.png`, `.webp` 琴譜檔案。
  2. **整合 `PDF.js` 多頁高清渲染**：
     - 針對瀏覽器直接雙擊 `file://` 開啟 `index.html` 時常見的 Web Worker 跨域限制，採用 `Blob + URL.createObjectURL` 包裝 `pdf.worker.min.js`，確保離線或本地直接開啟皆可 100% 正常解析多頁 PDF。
     - 以 `scale = 2.0` 二倍高清像素渲染每一頁 PDF（例如《償還_Am.pdf》共 2 頁，渲染為 `1190 × 1684 px` 高清畫布），並支援「上一頁 / 下一頁 / 第 1 頁、第 2 頁快捷鈕」瞬間切換。
  3. **內建範例一鍵免選檔載入 (`js/sample-sheets-data.js`)**：
     - 將備份於 `samples/` 的《償還_Am.pdf》(2頁 PDF) 與《川の流れのように_C.jpg》(JPG) 封裝為離線 Base64 模組，在 `file://` 下無須架設本地 Server 即可一鍵載入兩份真實琴譜並自動同步原調與建議目標調。
  4. **無損縮放與雙層畫布結構**：支援 `50% ~ 175%` 縮放預覽，並在 `#sheetBaseCanvas` 正上方對齊建立 `#sheetOverlayLayer`，為下一步 `T2-2` 與 `T2-3` 的和弦座標標註與替換做好準備。
  5. **修復 `file://` 下 PDF.js Fake Worker 載入錯誤 (`ISSUE-005`)**：
     - 實測發現 `file://` 環境下瀏覽器會強制使 PDF.js 進入 Fake Worker（主執行緒）模式，原先以 `Blob(importScripts)` 設定 `workerSrc` 會在主執行緒因找不到 `importScripts` 而報錯 `WorkerMessageHandler undefined`。
     - 改於 `index.html` 直接以 `<script>` 引入 `pdf.worker.min.js`，讓全域 `window.pdfjsWorker.WorkerMessageHandler` 直接就緒，徹底解決 `file://` 本地開啟 PDF 的問題。

## 📅 2026-11-21：Gemini 伺服器高負載卡死防禦、即時秒數計時與取消機制實作 (ISSUE-007)

### 18. 實測遭遇 High Demand 與請求懸掛當機分析與全面防禦
- **問題現況**：
  - 使用者辨識樂譜時連續遇到兩次 Google 官方錯誤 `This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later.`，隨後第 3 次呼叫時，請求卡死在「⏳ 正在辨識全曲進度：第 1 / 2 頁...」長達 5 分鐘，按鈕鎖定無法中斷。
- **原因分析**：
  - Google Gemini 伺服器在全球高峰時段若過載，可能掛起 HTTP 連線不釋放；原前端程式缺乏超時機制（Timeout）與 Abort 控制器，導致瀏覽器無限期空等，造成畫面呈現假死狀態。
- **改善措施**：
  1. **25 秒強制逾時保護 (Timeout)**：於 `js/sheet-parser.js` 實作 `callGeminiApiWithRetry()`，請求超過 25 秒自動斷開並解鎖按鈕，絕不再讓使用者乾等。
  2. **High Demand 自動退避重試**：遇到 503 / 429 或 High Demand 錯誤時，自動在背景倒數等待 3 秒並重試最多 2 次，不需使用者手動重按。
  3. **動態秒數計時與動畫提示**：辨識中文字即時更新 `(已耗時 X 秒...)`，是否正在運行一目了然。
  4. **提供「🛑 取消辨識」紅色按鈕**：辨識中可隨時手動一鍵中斷，秒解鎖按鈕。
